## 二、结论

**没有发现需要紧急修复的性能问题。**

- 启动 45 ms、面板 7–17 ms、堆 2.8 MB、单次存档写入 0.2 ms，全部处于健康区间。
- **没有内存泄漏型结构**：`logs` 已经封顶
  （`this.s.logs=this.s.logs.slice(0,80)`），不会随游玩时长无限增长。
- **存储不会爆**：单档 3,388 字符（含备份约 6.6 KB），推算 100 档约 **0.65 MB**，
  远低于 localStorage 常见的 5 MB 上限。
- **脚本不是瓶颈**：只占 25%。想靠"优化 JS 字符串拼接"提速，收益上限就是 1.25 ms。

## 三、唯一值得做的优化：减少布局抖动

**问题**：`render()` 每次交互都重建整个应用：

```js
function render(){
 renderStatus(); renderScene(); renderMap(); renderPeek(); renderTravel(); renderPanel(); syncLayers();
 ...
}
```

而 `renderPanel()` 在**写完 5 个容器的 innerHTML 之后**才去读 DOM：

```js
const old=$('panel-body')?.scrollTop ?? ...;
const warehouseOffsets=panel==='warehouse'?[...document.querySelectorAll('.warehouse-side-list')].map(e=>e.scrollTop):null;
const characterGearOffset=panel==='character'? ... document.querySelector('.character-gear-list')?.scrollTop :0;
const focus=document.activeElement, focusId=focus?.id, start=focus?.selectionStart, end=focus?.selectionEnd;
```

写 → 读 → 再写，触发**强制同步布局**，这就是每次交互出现 3 次 Layout 的原因。

**改法**：把这几处 DOM 读取提到 `render()` 的**最前面**（任何 innerHTML 写入之前），
存到模块级变量，`renderPanel()` 直接用变量。预计可把每次交互的 Layout 从 3 次降到 2 次。

**预期收益**：桌面端约省 1 ms；低端手机上按 3–5 倍放大，约省 3–5 ms/次。

**为什么我没有直接改**：`render()` 是全局重建入口，被所有交互路径调用。
改它要动 `render` 与 `renderPanel` 两个核心函数，回归面很大；
而当前收益只有个位数毫秒，属于**风险高于收益**。
如果要针对低端机型优化，建议单独开一轮、配完整的交互回归测试再动。

## 四、不建议做的

| 项 | 原因 |
|---|---|
| 优化 JS 字符串拼接 | 脚本仅占 25%，上限 1.25 ms |
| 合并 30 个样式表 / 1791 条规则 | 样式重算仅 0.75 ms；合并会打乱既有补丁式版本管理 |
| 存档写入防抖 | 单次 0.2 ms，且防抖会带来关页丢数据的风险 |
| 拆分单文件 HTML | 项目刻意保持自包含单文件，拆分会破坏分发方式 |

## 五、未覆盖

- **100 档全满时的存档与列表性能**：需要构造 100 个真实档位，本次未做。
- **图鉴全部展开时的 DOM 规模**：本次只测了折叠态（224 节点）。
- **低端真机**：本次是桌面 headless Chromium，真机放大系数未实测。
