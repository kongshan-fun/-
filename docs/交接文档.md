# 交接文档 · 山野修仙记（H5 文字修仙 / TapTap 小游戏）

> 用途：换环境重新立项时，按本文执行界面规范与发布流程。
> 所有数字、路径、结论均来自本项目的实测，不是推测。文中标注「教训」的地方，是已经踩过的坑。

## 一、一句话原则

**一页只放同一类内容。同类内容多了，滚动是正常的；多个不同功能塞进一屏再各自点击折叠，才是要禁止的。**

判定某个面板该不该拆，看的是**内容是否同质**，不是屏数。

### 曾经的错误判据（教训）

我一度拿屏数当标准，把下面三个误判为「必须拆」：

| 页面 | 屏数 | 错误判定 | 正确判定 |
|---|---:|---|---|
| 教程 | 3.11 | 要拆 | 同一篇连续正文，滚动合理 |
| 见闻 | 2.40 | 要拆 | 同类文本条目 |
| 炼制 · 品阶配方 | 1.45 | 要拆 | 同类配方 |

**不要复用「屏数 > 1 就是问题」这种判据。**

## 二、界面结构规范

### 2.1 允许滚动的页面（同类内容）

仓库 / 背包 / 图鉴**品类内条目** / 炼制品阶配方 / 教程正文 / 见闻

### 2.2 必须用父子页跳转的页面（多类功能）

| 面板 | 结构 | 父页实测（320/360/390） |
|---|---|---:|
| 修炼 | 父页 → 破境条件 / 境界法门 / 休整 | 1.35 / 1.15 / 1.00 屏 |
| 炼制 | 父页 → 品类 → 品阶 → 配方 | 1.10 / 1.00 / 1.00 屏 |
| 设置 | 父页 → 存档 / 寿元 / 角色 / 视觉 / 帮助 / 重整 | 1.23 / 1.05 / 1.00 屏 |
| 图鉴 | 父页（品类入口） → 条目 / 详情 | 1.01 / 1.00 / 1.00 屏 |

### 2.3 例外：本体内容不拆

**洞府 = 洞府本体。设施升级属于本体内容，不能做成「功能入口」子页。**

这是被明确纠正过的一次错误。判据是**从属关系**，不是内容多少：

- 设施之于洞府 → 本体组成部分 → **就地展示**
- 修炼之于洞府 → 一个功能 → **子页**

### 2.4 层级深度：三级封顶

`炼制 → 品类 → 品阶 → 配方` 已经三层（最深层 1.45 屏）。

再往下就是四层，**点击四次才看到内容，比滚半屏更烦**。第四层不如接受滚动。

### 2.5 实现约定（可直接照搬）

```js
// 子页判定
function isCultChild(p){return p==='cultivate-trial'||p==='cultivate-art'||p==='cultivate-rest';}
function isSetChild(p){return p==='set-save'||...;}

// 跳转动作：panel-step（可带 data-cat / data-tier）、cult-step
// 返回：panel-back 处理函数最前面按子页类型分流回父页

// 列表入口行样式：.cult-nav / .cult-nav-row（父页入口统一用它）
// 图鉴：bookCats() 品类表；book-cat-cell 入口 → filter=品类 → bookListBody()
//       动作 book-cat（进品类）/ book-home（← 返回图鉴）
```

子页头部统一显示「← 返回{父页名}」，标题进 `names` 映射表。

## 三、验收方法（这一节最重要）

### 3.1 必须截图验收，不能只看数值

**教训：** A/B/C 三版对比时，三版测量值**完全相同**（顶栏 45px / 状态条 74px / 可视 353px），我从数字判断「A 方案没生效」。截图一看：A 生效了，但把四条资源条压成了细线，**高度一分没省，内容全毁**。

> **数字相同的两种实现，可能一种是好的、一种是坏的。布局改动必须截图。**

### 3.2 必须多宽度验收

我前四轮所有「1.00 屏」结论都只在 **390×844** 一个尺寸成立。补测后：

```
320×568  洞府 1.87  图鉴 1.96  主线 1.44  设置 1.28   ← 全是红的
```

**单尺寸验收 = 假通过。**

### 3.3 基准尺寸与可视高度（实测）

| 尺寸 | 顶栏 | 状态条 | 面板可视区 |
|---|---:|---:|---:|
| 320×568 | 45px | 74px | **353px**（带工具栏的面板 306px，如图鉴搜索栏） |
| 360×640 | 42px | 74px | **413px** |
| 390×844 | — | — | **608px**（一屏 ≈ 6 张配方卡 / 4 行建筑卡） |

**教训：** 我曾凭截图估算「顶栏+状态条吃掉 230px」，实测只有 **119px**，差一倍。**估算不能代替测量。**

### 3.4 尺寸分档

- **320×568**：极小屏，可视仅 353px，一屏约 3–4 张卡片。**归"允许滚动"档**，不要求收敛。
- **360×640 以上**：要求收敛到一屏（1.02 屏以内算达标）。

**不要为 320 把字号压到 9px 以下**，可读性损失大于滚动成本。

### 3.5 验收矩阵脚本

`tests/v915_widths_matrix.cjs`：8 个面板 × 3 种宽度，输出屏数矩阵。每次界面改动都跑。

**V90.17 修过它自己的两个过期点**（结构变了测试不跟着变，就会把好状态报成坏状态）：

1. 修炼已改成洞府的子页，矩阵改成「先开洞府 → 再点修炼」，否则永远读到 `—`。
2. 「行记空态」那段原本用 `panel-back` 复位；遇到没有返回键的父页（洞府/设置）会残留，
   于是下一次点「设置」把已打开的面板**关掉**了，读到空内容 ——
   **产品其实早就修好了，是测试在骗人**。现在改成点 `close-panel` 硬复位，并断言
   「logs 为空必须出现占位文案」，PASS/FAIL 直接打印。

## 四、工程实践

### 4.1 适配层挂引擎方法，不挂 DOM（最值钱的一条）

TapTap 适配层的 5 个安装点全是**引擎方法**：`render()` / `persist()` / `bossWins` / 飞升上报。**没有一个挂在 DOM 节点上。**

结果：六轮 UI 重构把面板、顶栏、入口全换了一遍，适配层补丁 **5/5 全部命中**，一次移植成功。

**反例是我自己写的测试**——用顶栏「档案」按钮进游戏，按钮一删，21 项断言集体阵亡。

### 4.2 版本链构建 + 三条硬断言

每版从**冻结的上一版发布文件**构建：

1. 基线字节哈希校验
2. 每处替换的出现次数断言（防锚点漂移/重复命中）
3. **动作集合不得减少**（`data-a` 集合比对）

七轮重构（V90.11→V90.17）没丢失一个功能按钮，靠的就是第 3 条。

构建器命名：`tools/build_v9xx_from_main.py`，基线校验串写在文件头。

### 4.3 改结构必须同步改测试

本次两套测试因结构变化集体失效：

| 测试 | 失败数 | 真因 |
|---|---:|---|
| `v909_settings_browser` | 21 | 用顶栏档案按钮进游戏，按钮已删 |
| `v910_file_launch_check` | 1 | 断言「有档案入口」，已删 |

**不是产品坏了，是测试过期。** 但 21 条红灯会淹没真问题——每轮先分辨「回归」还是「过期」。

### 4.4 减去入口 > 压缩像素

顶栏 119px 里塞了 9 个信息单元（标题、两按钮、境界、道行、寿元、战力、日期、四条资源条），**压不动**，硬压就坏。

而一次减法（顶栏 3→2 按钮、背包外部入口 4→1）省掉的是整类决策成本，**比调 20 行 CSS 有效**。

### 4.5 CI 与浏览器验收（V90.24 起重做）

旧的 `v908-main-verify.yml` 把 **V90.8 的文件名、标题、哈希**写死在 YAML 里，发版当天就红；
旧的浏览器套件 `v908_browser_responsive.py` 同样钉死 V90.8，还写死 `channel="chrome"`（Windows 上没有 Chrome）。

现在：

| 件 | 作用 |
|---|---|
| `.github/workflows/main-verify.yml` | 唯一主校验。**按当前版本反查**，升版本不用改它 |
| `tools/check_entry_consistency.py` | 标题版本 ↔ 发布文件字节一致 ↔ 构建器 `OUT_NAME` 反查 + 基线哈希；`--rebuild` 额外验证"同输入重建出同字节" |
| `tests/browser_responsive.py` | 6 视口 ×（装备 2/3/10/36 件 + 百档 20 格 + 洞府建筑卡），断言真实 DOM 高度/滚动，产出截图到 `artifacts/browser-responsive/`；浏览器按 msedge → chrome → 自带 chromium 回退 |

**它真的抓到过东西**：V90.16 的窄屏密度补丁把 `#panel-root .building-card .building-effect`
写成**全局** `max-height:30px`（本意只想管窄屏），把 V90.8「说明不能被裁」的修复整段盖掉；
静态断言查不出来（那条修复规则还在文件里，只是被覆盖），只有浏览器量
`scrollHeight/clientHeight` 才现形 —— 六视口全部命中，于是有了 V90.24。

## 五、TapTap 发布流程（用官方 CLI，不是 MCP）

### 5.1 环境

```
Node      : D:\node\node.exe
TapTap CLI: D:\taptap-cli\node_modules\@taptap\cli\scripts\run.js
凭据      : C:\Users\<用户>\.taptap-cli\taptap.json（不要打印内容）
调用形式  : & "D:\node\node.exe" node_modules\@taptap\cli\scripts\run.js <命令> ... --json
            （先 cd D:\taptap-cli）
```

若报 401：`auth login --no-wait --json` 取 device code → 让用户扫码 →
`auth login --device-code <code> --expires-at-unix <ts> --interval-seconds 1 --json`（5 分钟过期）

### 5.2 ZIP 结构（关键约束）

平台要求**根目录恰好一个游戏目录**：

```
✓ shanhe_v916/index.html
✗ index.html                              → H5 ZIP root must contain exactly one game directory
✗ 目录名含反斜杠                          → MULTIPLE_ROOT_ENTRIES
```

**Windows 的 `Compress-Archive` / `.NET CreateFromDirectory` 会写反斜杠路径，不可用。**
必须手写 ZIP：`deflateRaw` + 手动 local header / central directory / EOCD，entry 名用 `/`。

现成工具：`tools/mk_taptap_zip.cjs`（已实现 CRC32、UTF-8 名称标志、回读 sha256 校验）。

### 5.3 四步流程

**① 上传包体**

```powershell
cd D:\taptap-cli
& "D:\node\node.exe" node_modules\@taptap\cli\scripts\run.js upload-h5-package `
  "assets\<包名>.zip" --dev-id <dev> --app-id <app> `
  --screen-orientation 1 --yes --json
```

读回 `data.h5PackageId`、`data.h5VersionId`、`data.packageSize`、`data.archive_preflight`
（`entry_count=1`、`violations=[]` 才算过）

**② 读当前主包位**（绑定要做乐观锁）

```powershell
... app list-packages --dev-id <dev> --app-id <app> --json
```

读 `data.result.current_bindings.package_id`（旧的包体 id）

**③ 绑定到草稿主包位**（请求体必须 `@file`，YAML/内联都不行）

```json
{"expected":{"h5_version_id":"<旧 id>","kind":"h5"},
 "package":{"id":"<①的 h5VersionId>","type":"h5"},"slot":"main"}
```

```powershell
... app select-package --dev-id <dev> --app-id <app> `
  --data '@req-bind.json' --idempotency-key bind-<唯一后缀> --dry-run --json
... app select-package ... --idempotency-key bind-<唯一后缀> --yes --json
```

成功返回 `package_id` / `revision` / `status:updated`

**④ 出自测码**

```json
{"package_id":<①的 h5VersionId>}     ← 用 h5VersionId，不是 h5PackageId
```

```powershell
... test-qr-code --dev-id <dev> --app-id <app> --data '@req-qr.json' -o selftest-qr.png --json
```

**必须把 PNG 作为图片附件展示给用户扫码，只给路径等于没交付。**

**⑤ 提交审核（高风险，必须用户明确要求）**

```powershell
... app precheck-app-review --dev-id <dev> --app-id <app> --data '@req.json' --json   # 只读
# blockers 为空、preaudit_passed=true 才继续
... app submit-app-review --dev-id <dev> --app-id <app> --data '@req.json' `
  --idempotency-key submit-<唯一后缀> --yes --json
```

**不能自己加 `--yes`**，必须用户明确说「可以发布」。

### 5.4 已知坑（都踩过）

| 坑 | 现象 | 处理 |
|---|---|---|
| 反斜杠 ZIP | `MULTIPLE_ROOT_ENTRIES` | 手写 ZIP，entry 名用 `/` |
| JSON 解析 | `ConvertFrom-Json` 报「应为 : 或 }」 | 先 `IndexOf('{')` 切掉 stderr 噪声 |
| JSON 文件 BOM | CLI 拒收 | `UTF8Encoding($false)` 写文件 |
| 幂等键冲突 | 409「同一 Idempotency-Key 已用于不同请求体」 | 换新 key 重传 |
| `-o` 目标已存在 | `output file already exists` | 换文件名或先删除 |
| 审核中改资料 | HTTP 400「游戏资料已提交或已过审」 | 只能等审核结束 |
| **PowerShell 改 UTF-8 源码** | `Get-Content -Raw` / `Set-Content -Encoding utf8` 会把中文按 GBK 往返，整份文件变成乱码，且有空格/引号被吃掉的风险 | **不要用 shell 改带中文的源码**；用编辑工具改，改完 `node tests/syntax_check.cjs` 复核 |

### 7.1 轮回玉广告奖励：已修（V90.18 加数额，V90.25 加次数）

**历史**：V90.18 把「领取100轮回玉」提到 200，但**没有次数限制** ——
浏览器/离线版点一次 +200，TapTap 包内每次点击都被广告拦截器接管成"看广告 +200"，
同样不限次数。按 `LIFE.initialYears=56`、出生站 10玉=+5年寿元换算，一次 = +100 年寿元
（初始的 2.8 倍、12.5 颗延寿丹），5 次 ≈ 一次飞升的基础结算。

**V90.25 的规则**：每个档位一次。

| 件 | 做法 |
|---|---|
| 标记 | 旁路键 `<key>-jadead`（照 `deathKey` 的约定），**不进 `legacy` 账本**（账本有结构校验，加字段会牵动存档格式/100 档回归/云存档 payload） |
| UI | 领过后按钮置灰显示「本档已领取」；说明行写「每档仅可领取一次，刷新或重开不会重置」 |
| 兜底 | 处理器里先查再发；即使外部把 `disabled` 去掉也发不出第二份 |
| 不串档 | 键里带档位号，002 领过不影响 003 |

验收：`tests/v925_jade_once.cjs` 19 项 —— 初始状态、+200、置灰、强行绕过被拦、
刷新重进不重置、换档可再领、种子档未被写入。

### 7.2 评价/加群入口为什么没做成"贴边悬浮"（V90.19，留档避免返工）

先说结论：**这个 HUD 在 320 宽下没有能放悬浮圆点的空位**，用浏览器实测：

```
320×568：资源格第 6 列右缘 x=308，卡片内缘 304，手机宽 320
         贴右缘 40px 圆点 = 直接盖住一颗资源（截图证据：visual/v919/ 第一版截图，已废弃）
```

所以改成**场景卡标题行里的一个小标点**（标题与危险度徽章之间，44×20），
由 flex 天然让位，永不压住任何内容；面板打开时随场景一起被覆盖，`renderPromo()` 也会清空插槽。

规则：
- 一次性标记是**全局键** `shanye-promo-v1`（玩家级，不进 slot 存档，不碰 normalize / 100 档回归）
- 点开弹窗时立刻写入标记 → 关掉后刷新也不再出现（`tests/v919_promo.cjs` 27/27，含刷新断言）
- **弹窗文案里不出现"奖励"二字**（V90.20 用户要求）；评价只做文字引导，不跳转外链
- 群号与用途写在 `tools/build_v920_from_main.py` / `build_v921_from_main.py` 的文案常量里，改完重跑构建器
- 320 宽下弹窗实测 376~396px < 568，不出现内部滚动（`tests/v920_modal_narrow.cjs`）

### 7.3 评价入口的显示条件（V90.22 起，代码只有一行）

`promoVisible()` 为真才显示「★ 评价」，全部条件同时满足：

```js
!promoSeen()                 // 没点开过（全局键 shanye-promo-v1，点开即永久关闭）
 && !!game && !!activeRole   // 已在游戏中
 && !frontPage               // 不在选角/档位/命格这些前页
 && !deathBoot               // 不在寿尽/飞升结算态
 && !panel                   // 没有打开任何面板
 && !game.s.combat           // 不在战斗中
 && (game.s.guide.status==='done' || game.s.guide.status==='skipped')
                             // ↑ 跟完新手教程，或跳过新手教程
```

补充事实：
- 它是**条件驱动**，不是事件驱动：满足就一直在场景卡标题行里，直到点开一次
- V90.22 之前这条是 `game.camp||game.day>=2`（有洞府 / 第 2 游戏日），时机偏早：
  第 2 日可能只采了两把草，玩家还没真正"玩过"
- 跳过教程走的是 顶栏「教程」面板里的「跳过引导」，该动作本身会 `panel=null`（面板自动收起），
  随后一次 `render()` 就把标点放出来
- 显示位置在**主场景卡**（`#promo-slot`）；秘境卡、战斗卡没有这个插槽，天然不显示
- 打开面板时 `renderPromo()` 清空插槽，关闭面板后 `render()` 再放回来
- 点开后立刻写标记 → 即使不点「知道了」直接关弹窗，也不会再出现
- 验收：`tests/v922_promo_trigger.cjs` 覆盖 new / active → 不出现，skipped → 出现；
  `tests/v919_promo.cjs` 用种子档（guide=done）覆盖"跟完"这条路径

### 7.5 360×640 收敛进度与「洞府为什么还停 1.51」

V90.26 / V90.27 三连收敛后的 360×640 实测（面板可视 413px）：

| 面板 | 之前 | 现在 | 做法 |
|---|---:|---:|---|
| 设置父页 | 1.05 | **1.00** | 删掉「分区之间互不影响…返回设置」整句（子页自带返回按钮，信息重复） |
| 修炼父页 | 1.15 | **1.00** | 删「四游戏日折一年…」段（帮助·寿元章有）；「试剑与法门…」压成一行 |
| 主线父页 | 1.23 | **1.00** | `≤400px` 收行高：入口行 62→42、见闻行 59→42、任务卡内边距收 2~4px |

**洞府为什么压不下来**（实测数据，避免下一轮白试）：
- 组成：洞府摘要 66.5 + 功能行 34 + 灵田条 39 + 标题 21 + **设施网格 407.6**（6 张卡 × 3 行 × ~135）
- 光是设施网格就 407.6px，已经吃掉 413px 的可视区；卡片里要放「名称/等级 + 效果 2~3 行 + 材料 + 按钮」
- 想把卡片压到 84px 需要把效果文字砍成 1 行 —— 而这正是 V90.24 刚修好的「不裁文字」契约
  （浏览器验收会立刻红），也可能违反「本体内容不拆」这条原则
- 结论：**1.02 在 360 下与「设施就地展示 + 不裁文字」不可兼得**。要真收敛，需要产品决策：
  ① 接受 1.5 屏滚动（本体内容，符合"同类内容滚动合理"）；

### 7.4 装备来源规则（V90.23 起，A 方案）

**成品装备的唯一来源是炼器室炼制。** 战斗与秘境只给器材。

| 来源 | 改动前 | 改动后 |
|---|---|---|
| 普通怪 | 22% 掉成品 | 不掉成品（原有的 `e.loot` 材料照旧） |
| 首领 | 必掉成品（品质保底≥精良） | `dropLoot()`：本境主材×2 + 副材×1 + 灵尘 |
| 秘境封藏 | 32% 掉成品 | 32% 掉该秘境专属灵材×1 |
| 一次性奇遇·遗迹寻宝 | 掉成品 | **保留**（一次性、有前置条件，属"发现"不属"刷"） |

为什么必须这么改（实测，不是推测）：`createGear` 对**炼制与掉落用同一个**
`rollQuality(zone)` —— 品质分布完全一样；而掉落还多一层 `min=1` 保底，
且零材料成本、`acceptGear` 自动换装。等于"打怪白拿的比炼的还好"，
采集—炼制循环被彻底旁路（每境白拿 ≈ 5.4 件，而该境可炼成品只有 2 件 + 1 件秘藏专属）。

改动后经济自洽性（`tools/audit_gear_sources.cjs` 实测）：
- 首领掉落 **正好等于**同境装备配方的材料需求（只差采集来的灵木/青藤）→ **杀一次首领 ≈ 一件装备的料**，
  想同时要剑和甲就得再采集或再刷
- 每境可炼成品 2 件（剑/衣）+ 秘藏专属 1 件，全档合计 26 件
- `tests/v923_gear_drop.cjs` 锁死：`dropGear(` 只允许出现 2 次（定义 + 奇遇），
  战斗行必须是 `if(boss)this.dropLoot();`

**以后别再给战斗加成品掉落**，否则又回到"打怪就够、不必采集"。要加产出就加器材或灵尘。
