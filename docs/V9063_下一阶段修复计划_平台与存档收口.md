5. 旧存档（无 `rebuilt` 标记）按已决定的重构策略进入“导出旧档 → 手动确认从零开始 → 阶梯轮回玉补偿”流程。现有逻辑已保护重复发奖，但**旧角色进度不能直接迁移**，重置时原档/自动备份会被替换或清理。不能把此流程称作“无损升级”。

## 二、范围与不可变约束

- **不增加玩法**：不扩地图、妖兽、装备、境界、抽卡、商城；不擅自改变 V90.62 数值、掉率、12 境/36 段、飞升、寿元和炼制规则。
- **不覆盖存档**：调试仅用隔离测试档与合成数据；真实旧档需在操作前保留独立副本和校验和，不能用真实玩家的唯一副本开展故障注入。
- **不要改变广告商业规则**：V90.29 决定“每次完整观看可重复获得 100 轮回玉”，不是每档只能领一次；本阶段修复的是**单次观看回调重复发奖/中断发奖**，不限制正常再次观看。
- **发布分层**：GitHub main 已合并；TapTap “包体上传 → 绑定/自测 → 提交审核 → 审核通过 → 发布”互不等价。除非获得明确发布指令和通过所有门禁，不绑定正式包位、不提交审核、不发布、不修改正式玩家数据。
- 每个修复提交留精确 BASE_SHA、最终 SHA、具体测试原始日志和回滚文件；不删失败测试、不伪造通过截图、不凭静态关键字宣称平台功能通过。

## 三、执行工作包（按依赖顺序）

### P0-01｜TapTap 适配与构建可复现（第一件事）

**症状/证据**：`build_taptap_v962_from_v9062.py` 依赖仓库外 `shanhe-v907/taptap/taptap-adapter.js`，且当前 CI 主要验证独立 H5，而不是重新从锁定依赖构建的真实 TapTap 产物。

**实施**：
1. 找到已上传 `350466` 对应的原始平台 ZIP、`build-manifest.json`、实际适配层源码；逐一核对内嵌 `buildCode`、源 HTML 的 SHA-256、成品 index SHA-256、ZIP SHA-256。若缺任何证据则标记 `NOT_VERIFIED`，不能推断一致。
2. 在合法可维护的前提下将平台适配源码纳入版本管理，或固定使用可取得、明确版本和 SHA-256 的依赖工件；不得把凭据、用户标识或平台私密配置写入 Git。
3. 平台专用构建器加固：校验输入 SHA、适配层 SHA、有效注入锚点的数量和实际作用，禁止关键平台接口被 `SKIP` 却仍判为可发布。
4. 从干净工作区独立重建，产物与指定上传包比对；如无法匹配需查清差异并重新生成 **新测试候选**，不得悄悄覆盖已上传记录。

**通过门槛**：`BUILD_PROVENANCE=PASS`，仓库/锁定依赖可复建，真实平台包版本与提交一一对应；平台 ZIP 清单和哈希完整；无未声明外部构建依赖。

### P0-02｜旧档重置与补偿不可逆风险

**症状/证据**：旧档无 `rebuilt` 标记会走重构重置，旧主档与自动备份在玩家确认后可能丢失。已经通过“补偿不重复”的专项，但不是进度兼容迁移。

**实施**：
1. 对 V90.35 / V90.37 等实际旧版测试档建立不可变样本，覆盖人族/妖族、空档/高境/飞升/已领取/已消费补偿、断电/配额不足；在测试前后保留完整 JSON、版本、来源、SHA。
2. 明确产品选择：A 保持“旧档不直接迁移、明确确认重置+补偿”，但必须保证原始旧档先有**可复读的独立归档**；B 若要求无损迁移，则应另立迁移专项、做字段映射和回滚，不可在本版擅自承诺。
3. 如选 A，归档成功及内容校验后才能允许继续重置；失败时保留旧档、不重置、不重复发奖。已领取但消费过轮回玉，不显示再领提示。
4. 不同角色、档位、轮回账本互不串改；重复打开、刷新、双标签、存储故障重试保持幂等；不要以“点击过导出”假定用户已成功取得备份。

**通过门槛**：200/200 双种族档、异常写入场景、真实浏览器导出/取消/确认/重复打开全绿；模拟损坏情况下原始旧档可单独恢复；无未告知的不可逆数据删除。

### P0-03｜TapTap 云存档冲突与断线安全

**证据边界**：交接文档只证实旧策略“有本地档就不自动拉云端”，不代表此策略对跨设备是安全的；平台 SDK 的真实回调状态尚未验证。

**实施**：
1. 以当前适配层实际接口为准，审查下载/上传、节流、原子性、过期/重复回调、切出/返回、退出前补传；不要假设浏览器 `pagehide` 能保证完成网络上传。
2. 本地和云端均有存档时，不允许静默用旧数据覆盖较新数据；使用版本/修订号和来源信息识别冲突，时间戳仅作辅助（设备时钟可能不准确）。出现无法确定优先级时向玩家展示“保留本机 / 恢复云端 / 导出两份”，明确后再写。
3. 设置页可见最后一次**成功完成**的同步时间及失败原因，不把“开始上传”当作“已同步”。
4. 对页面隐藏/退出、网络中断、跨设备不同档位、轮回账本和存档删除标记进行一致性/冲突测试；关闭/重开后不复活已删除档或重复领取补偿。

**通过门槛**：双设备同账号、离线后重连、上传/下载中断、错时钟和跨 200 档的指定矩阵可追踪、无静默进度倒退；真实 TapTap 容器测试留屏幕/日志证据。

### P0-04｜激励广告完成态与奖励账本

**证据边界**：仓库 H5 会降级到 MOCK；浏览器模拟成功不等于真实 TapTap 广告成功。

**实施**：
1. 审查实际平台广告的预加载、展示、关闭、完成、失败与取消回调，建立“单次广告请求 ID → 完整观看确认 → 仅一次发奖 → 已保存回执”状态流。
2. 对四类入口（命格额外次数、轮回玉 +100、续命 +10 年、寿尽救援 +15 年）逐一验证业务条件，不因双击/重复回调/页面切换而重复发奖；没有真实完成回调不发奖。
3. 广告加载失败或余额写入失败要可恢复；继续支持正常多次观看获得 100 玉，不重新引入 V90.25 每档一次限制。

**通过门槛**：真实平台下每一次完成观看最多且恰好发放一次对应奖励；取消、失败、超时发放 0；重复回调/快速点击不多发；留保存后的轮回账本证据。

### P1-05｜真实容器与 UI/流程验收

- 使用已经上传的 `h5VersionId=350466` 对应二维码进入**自测**，实时确认该包仍存在且身份相符；先不要绑定正式主包位。
- Android/iOS（如可用）、360×640/390×844 和不同长屏：旧档弹窗、装备第三件第二行、36 件装备滚动、详情固定尺寸、战斗、破境、洞府以及底部安全区均做真实点击和截图。
- 旧档和新档各跑：战斗中保存与刷新、金丹前直接晋升/金丹起渡劫、修为超额跨境继承、已领奖再次打开。验收先确认实际 TapTap SDK 与 MOCK 状态。
- 平台排行榜/成就可单独降级或阻断发布：根据当前产品入口的重要性列出真实成功、失败、无网络时 UI 反馈，不伪称提交成功。

**通过门槛**：平台核心路径全部 PASS；无阻挡操作的布局问题、冷启动未捕获异常、严重性能冻结；截图按设备、游戏版本及测试码归档。

### P1-06｜发布门禁与回滚

- 先冻结本阶段最终提交和所有产物 SHA；运行 43/43 历史回归、65/65 存档专项、200/200 故障注入、11 项浏览器旧档操作和 6 视口矩阵，再加真实 TapTap 环境矩阵。
- 报告逐项写 `PASS / FAIL / NOT_TESTED`，不把没有设备或没有平台授权记为 PASS。
- 在后台回读在线版本、当前绑定包、审核/草稿状态；记录可回滚的上一版包和玩家数据处理方案。
- 只有 P0 全绿、完整 OWNER 审批后，才能进入“绑定 → 提交审核 → 上线”。正式操作需另行明确指令。

## 五、实施方法和停止条件

1. 从当前 `main` 创建独立工作分支（建议 `fix/v90.63-platform-save-ad`），只在其上开发；必须锁定父提交 SHA。
2. 先跑已通过的基线矩阵。每项失败先给可复现的最小样本，再实施代码改动，禁止靠删除测试或放宽关键断言取得绿灯。
3. 执行顺序固定：**平台构建来源 → 旧档安全 → 云存档 → 广告 → 真机 UI → 发布包核验**。某一项无法在当前权限/设备完成，就标为 `BLOCKED`，不跳步伪造完成状态。
4. 交付：源码 Diff、构建脚本、版本化适配层或锁定依赖、独立 H5、TapTap 自测 ZIP、SHA256SUMS、测试原始日志、真实截图、风险清单、回滚说明和 OWNER_REVIEW。
5. 修复范围原则上在 V90.63 内收口；若旧档无损迁移涉及大量历史业务规则，应单列后续专项，**不要把原 V90.62 的用户数据风险藏在发版说明里**。
