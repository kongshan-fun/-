# 交接提示词（复制下面整段，作为新项目的第一条消息）

```
你是这个项目的主力开发。项目是「H5 单文件文字修仙游戏」，最终以 TapTap 小游戏（关卡/创意工坊形式）发布。
先读这三份文件，再动手：
  docs/交接文档.md          ← 界面规范、验收方法、发布流程（必读）
  docs/界面层级重构原则.md   ← 已落地的父子页结构与代码约定
  tools/                     ← 版本链构建器与手写 ZIP 工具

## 一、界面铁律（不可违背）

1. 一页只放同一类内容。同类内容多了，滚动是正常的、允许的。
2. 多个不同功能塞进一屏、再各自点击折叠 —— 这是禁止的「下拉条」反模式。
3. 功能之间用页面跳转：父页入口行 → 子页 → 「← 返回父页」。不做折叠、不做折叠面板。
4. 判定某页该不该拆，看「内容是否同质」，**不看屏数**。
   已知反例：教程(3.11屏)、见闻(2.40屏)、炼制品阶配方(1.45屏) 都是同类内容，
   滚动合理，**不要拆**。
5. 例外：本体内容不拆。例：洞府的「设施升级」属于洞府本体，必须就地展示，
   不能做成「功能入口」子页。判据是从属关系，不是内容多少。
6. 层级深度三级封顶（品类 → 品阶 → 配方已是三层）。第四层不如接受滚动。

## 二、验收硬要求

1. **布局改动必须截图验收。** 数字达标不等于视觉正确——
   曾出现三版测量值完全相同、但其中一版把资源条压成细线的案例，
   只看数值会漏掉「损坏但等高」。
2. **必须多宽度验收**，至少 320×568 / 360×640 / 390×844。
   只用 390×844 验收是假通过（曾导致 320 下 6 个面板全部超屏）。
3. 基准：390×844 面板可视 608px；320×568 可视 353px
   （顶栏 45px + 状态条 74px = 119px）。
4. 320×568 归「允许滚动」档，不为它把字号压到 9px 以下。
   360×640 以上要求收敛到 1.02 屏以内。
5. 每次界面改动跑 `tests/v915_widths_matrix.cjs`（8 面板 × 3 宽度）。

## 三、工程约束

1. 版本链构建：每版从**冻结的上一版发布文件**构建，带三条硬断言：
   ① 基线字节哈希 ② 每处替换出现次数 ③ **动作集合不得减少**（data-a 比对）
2. **平台适配层挂引擎方法（render/persist/bossWins/上报），绝不挂 DOM 节点。**
   这样 UI 怎么重构，适配层锚点都不会失效（已验证六轮重构 5/5 命中）。
3. 改结构必须同步改测试。否则测试集体失效产生 21 条红灯，
   会把真正的问题淹没——每轮先分辨「回归」还是「测试过期」。
4. 减入口优于压像素。顶栏塞满 9 个信息单元时压不动，硬压就坏；
   删掉重复入口一次省掉整类成本。

## 四、TapTap 发布流程（用官方 CLI，不要用 MCP 上传）

环境：Node `D:\node\node.exe`；CLI `D:\taptap-cli\node_modules\@taptap\cli\scripts\run.js`
凭据：`~/.taptap-cli/taptap.json`（**不要打印内容**）
形式：先 cd 到 CLI 目录，`& "D:\node\node.exe" node_modules\@taptap\cli\scripts\run.js <命令> ... --json`

四步：
1. `upload-h5-package` — 读回 h5PackageId / h5VersionId / archive_preflight
   （entry_count=1、violations=[] 才算过）
2. `app list-packages` — 读 current_bindings.package_id（旧 id，绑定要乐观锁）
3. `app select-package --data '@req-bind.json'` — 先 `--dry-run` 再 `--yes`
   请求体：`{"expected":{"h5_version_id":"<旧id>","kind":"h5"},
             "package":{"id":"<新h5VersionId>","type":"h5"},"slot":"main"}`
4. `test-qr-code --data '{"package_id":<h5VersionId>}' -o xxx.png`
   **必须把 PNG 作为图片附件展示给用户扫码，只给路径等于没交付。**

发布（高风险）：先 `precheck-app-review`（只读，blockers 为空才继续），
再 `submit-app-review`。**不能自己加 --yes，必须用户明确说「可以发布」。**

ZIP 结构：根目录必须恰好一个游戏目录（`shanhe_xxx/index.html`）。
Windows 的 Compress-Archive / .NET CreateFromDirectory 会写反斜杠导致
MULTIPLE_ROOT_ENTRIES，**必须手写 ZIP**（entry 名用 `/`），
现成工具 `tools/mk_taptap_zip.cjs`，打完回读解压比 sha256。

## 五、明确不要做的事

- 不要用 TapTap MCP 的 upload_h5_game 上传（它会直接进审核并自动发布，
  没有「只传不发布」的开关）
- 不要用 Compress-Archive 打 ZIP
- 不要自己给 submit-app-review 加 --yes
- 不要为窄屏把字号压到 9px 以下
- 不要凭记忆断言线上版本，一律 `app list-app-versions` 实时回读
- 不要只贴路径不贴图（二维码、对比截图都必须内嵌展示）

3. 设置 / 洞府窄屏：320 下 1.23 / 1.82 屏，边际收益低，可不做

开始工作前，先跑一次验收矩阵 + `app list-app-versions` 确认当前真实状态。
```
