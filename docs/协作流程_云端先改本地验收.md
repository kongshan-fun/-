# 协作流程：云端先改，本地再验收

> 2026-10-22 定。以后所有 bug / 小需求都走这个循环。

## 一、流程

```
1. 本地复现定位（找出根因、给出期望行为）
        ↓
2. 输出一份「可直接复制的纯文字问题清单」给云端
   （只写现象 + 期望 + 线索，不贴代码——云端自己查）
        ↓
3. 云端在新包基线上修改，产出新 HTML
        ↓
4. 本地拿到新包 → 跑验收矩阵 → 出结论
        ↓
5. 通过 → 上传测试包 → 真机验证 → 发布
   不通过 → 把失败项写成新的问题清单，回到第 2 步
```

## 二、第 2 步：问题清单怎么写

固定四段，不贴代码：

```
一、现象（原话/数字，越具体越好）
二、期望行为（改完后应该是什么样）
三、线索（可选：一句话根因方向，比如"存档时会重建某段数据，那段代码用错了上下文"）
四、是否顺带影响别处（可选）
```

**不写代码的原因**：云端包与本地包版本可能不同，贴代码容易贴错锚点；让对方自己定位反而更稳。

## 三、第 4 步：本地验收矩阵（每次必跑）

| 层 | 检查内容 | 通过标准 |
|---|---|---|
| 语法 | 所有 script 块编译 + 自包含 | 0 错误、无外链 |
| 版本 | `index.html` 与发布文件 | 字节一致 |
| 功能 | 本次改动对应的验收脚本 | 全通过 |
| 回归 | `run_full_regression` | 原有层全绿 |
| 布局 | 浏览器多视口（320/360/390/412/1080/1440） | 全部 PASS |
| 存档 | 战斗中和战斗外各存一次 + 刷新后数值一致 | 无异常、数值不变 |

**不许跳过**：不改测试来"变绿"；旧断言与新政策冲突时标注废弃并说明原因，不整层删除。

## 四、版本与记录

- 云端每版给：文件名、字节数、内置版本号（页面 `<title>` 里那个）
- 本地每版记录：SHA-256、验收结果、未验证项（如真机）
- 版本号纯数字（V90.61、V90.62），禁止字母后缀
